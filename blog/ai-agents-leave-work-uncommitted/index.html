AI coding agents leave work uncommitted: how to find it and make them save it

2 Nov 2026

Finished work that only exists on one disk isn't finished. Check for it on every machine, and stop the agent before it walks away.

If AI agents write code on your machine, some of that code is not saved anywhere else. Not committed, or committed and never pushed, or sitting in a folder that was never a git repository. It looks finished in the agent's summary. It is one dead disk away from gone.

On 31 October I scanned one build machine that agents work on every day: 214 project folders. 19 repositories had uncommitted changes. 8 had 15 commits that no remote had. 5 repositories had no remote at all, so their 7 commits existed only on that disk. 2 stashes had been left behind. On top of that, 1,065 folders held source files outside any repository. The biggest groups were working copies agents had made for one-off review runs, which is noise, but noise that hides the real misses.

None of this is a failure of any one agent. An agent's turn ends when the task looks done. Committing and pushing is a separate step, and nothing reminds it. A person forgets the same way, just more slowly.

The five ways work goes unsaved

  1. Uncommitted files. Changed or new files that git status lists. The most common one, and the easiest to see.
  2. Unpushed commits. Committed on a local branch, but no remote has them. git status only tells you about the branch you're on, so commits on other branches stay invisible.
  3. No remote. A repository that was created with git init and never connected anywhere. Every commit in it is local. This is the one that hurts most, because it looks properly saved.
  4. Stashes. Work set aside with git stash and never picked up again.
  5. Not in git at all. A folder of scripts next to the repositories, never added to one.

Find it with plain git

You don't need a tool for a first look. Run this from the folder that holds your projects. It visits every repository below it and prints anything unsaved:

find . -name .git -type d -prune | while read g; do
  r=${g%/.git}
  cd "$r" || continue
  dirty=$(git status --porcelain | wc -l)
  unpushed=$(git log --branches --not --remotes --oneline | wc -l)
  remotes=$(git remote | wc -l)
  stashes=$(git stash list | wc -l)
  if [ "$dirty$unpushed$stashes" != "000" ] || [ "$remotes" = 0 ]; then
    echo "$r: $dirty uncommitted, $unpushed unpushed, $remotes remotes, $stashes stashes"
  fi
  cd - >/dev/null
done

Two lines do the real work. git status --porcelain prints one line per changed or untracked file. git log --branches --not --remotes prints every commit on any local branch that no remote branch contains, which catches the branches git status doesn't show.

For folders that were never in git, look for source files outside every repository:

find . -name .git -prune -o -type f \( -name '*.py' -o -name '*.js' -o -name '*.go' -o -name '*.sh' \) -print \
  | while read f; do git -C "$(dirname "$f")" rev-parse 2>/dev/null || echo "$f"; done

Expect noise here: build output, dependencies, copies. Skim it once, then write the noisy folders down so the next scan skips them.

Save what's safe to save

Some of what you find you can save without thinking. A branch that is ahead of its own upstream and not behind it can be pushed as a fast-forward. Nothing on the remote gets overwritten:

git fetch
git status -sb            # "## main...origin/main [ahead 2]" means safe to push
git push

Leave the rest for a person, or for the agent that made it: diverged branches, branches with no upstream, uncommitted files. Those need a decision about what the work is and where it belongs. Never force-push to clean up a list.

Stop the agent before it walks away

A daily scan catches what was left behind. It's better to stop it from being left in the first place. Claude Code runs a Stop hook when the agent is about to end its turn. If the hook exits with code 2, the turn doesn't end: the agent reads what the hook wrote to standard error and keeps working.

A minimal version checks the repository the agent was working in:

#!/bin/sh
# ~/.claude/hooks/save-first.sh: refuse to stop while this repository has unsaved work.
input=$(cat)
# Ask only once per stop, so an agent with a good reason can still finish.
echo "$input" | grep -q '"stop_hook_active": *true' && exit 0
cd "$(echo "$input" | sed -n 's/.*"cwd": *"\([^"]*\)".*/\1/p')" 2>/dev/null || exit 0
git rev-parse 2>/dev/null || exit 0
dirty=$(git status --porcelain | wc -l)
unpushed=$(git log --branches --not --remotes --oneline | wc -l)
[ "$dirty" = 0 ] && [ "$unpushed" = 0 ] && exit 0
echo "Not saved yet: $dirty uncommitted files, $unpushed unpushed commits. Commit and push your work, or say why it should stay." >&2
exit 2

Register it in ~/.claude/settings.json:

{
  "hooks": {
    "Stop": [
      { "hooks": [{ "type": "command", "command": "sh ~/.claude/hooks/save-first.sh" }] }
    ]
  }
}

Three things I learned running a hook like this:

  • Check only the agent's own changes. When two agents share a repository, a hook that demands a clean git status makes one agent commit the other's half-written files. Read the session's transcript (its path is in the hook's input as transcript_path) and check only the files this session wrote.
  • Ask once. The input says stop_hook_active when the agent is already continuing because of a stop hook. Let it finish the second time. Some work should stay uncommitted, and an agent that can't stop just loops.
  • Leave scheduled jobs out. A script that commits for its agent at the end doesn't need the hook. Give it an environment variable that turns the hook off for that process.

If you want it done for you

I put the scan and the hook together as unsaved, open source under MIT. It reports all five kinds across many folders, pushes only what's safe with --push, and its Stop hook checks only the files the current session changed. It exits with 1 when something is unsaved, so a cron job or CI step can act on it.

go install github.com/taktekhq/unsaved@latest
unsaved ~/projects

Whichever way you do it, do it on every machine an agent touches, and look at the list once a week. The day a disk fails, the only work that counts is the work that's somewhere else.
