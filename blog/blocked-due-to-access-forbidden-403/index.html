"Blocked due to access forbidden (403)" in Search Console: what it means, and how to fix it

30 Oct 2026

A 403 is your server's choice. Find which layer made it: the host's firewall, a security plugin, a password, or a country block.

"Blocked due to access forbidden (403)" is a Search Console status. In plain words: Google asked your server for a page, and the server answered with the code 403 Forbidden, which means "I understood you, and you may not have this". Google doesn't index a page that answers 403, and a page already in Google that starts answering 403 drops out over time. Google's own HTTP status page says so for every 4xx code except 429.

On 30 October I asked the home pages of 101 of the most visited domains (the public Tranco top list) three times each: once as a normal Chrome browser, once with Googlebot's name in the request, and once as plain curl. As a browser, 4 answered 403. As "Googlebot", 12 did. 8 big sites, among them wikipedia.org, x.com, tiktok.com, wordpress.com and office.com, served the page to the browser and refused the fake Googlebot.

That isn't those sites blocking Google. They are blocking me pretending to be Google: my requests came from an address that isn't Google's, so their filters treated the name as a lie. It's the right behaviour, and it's the main thing to understand about this status. A 403 is a decision by some layer in front of your page, based on who is asking and from where. Below is how to find which layer, and why the obvious test misleads.

The words, translated

  • 403 Forbidden: the server got the request and refuses to serve it. Not "missing" (that's 404), not "broken" (that's 5xx).
  • 401 Unauthorized: the near twin. The server wants a login. Search Console shows it as a separate status, "Blocked due to unauthorized request (401)". Most fixes below apply to both.
  • User agent: the name a visitor gives in each request. Chrome sends a long string with "Chrome" in it, Google's crawler sends one with "Googlebot". Anyone can type any name.
  • Firewall (or WAF, web application firewall): a filter in front of your site that decides who gets through. Cloudflare, your host, and security plugins all run one.

This is different from "Blocked by robots.txt". There, your robots.txt file asks Google not to fetch the page, and Google obeys without asking. With a 403, Google did ask, and the server said no.

Why "test it as Googlebot" proves nothing

The common advice is to send a request with Googlebot's user agent and see what comes back. My reading shows both ways it goes wrong:

  • A 403 to your fake Googlebot doesn't mean Google is blocked. Good firewalls check the address too. Google publishes how: a real Googlebot address looks up to a name ending in googlebot.com, google.com or googleusercontent.com, and Google lists its crawler addresses in public JSON files. Your laptop fails that check, so you get the 403 and the real crawler doesn't.
  • A 200 to your fake Googlebot doesn't mean Google gets in. A rule that blocks a country, or a cloud network, or too many requests in a minute, can pass your request and stop Google's.

The answers also disagreed in a third way. facebook.com, whatsapp.com and wa.me answered 400 to my browser-like request and 200 to plain curl. A request that claims to be Chrome but doesn't behave like Chrome looks suspicious. Filters judge the whole request, not only the name.

So the only test that counts is one that comes from Google.

Step 1: ask Google to fetch the page

  1. In Search Console, open Indexing → Pages, click the "Blocked due to access forbidden (403)" row, and copy one of the example addresses.
  2. Paste it into the search bar at the top (URL Inspection) and press Enter.
  3. Click Test live URL. Google fetches the page now, from its own addresses.
  4. Open View tested page → More info. It shows the status code Google got.

If the live test now passes, the block was temporary or already fixed: click Request indexing and go back to the report to start validation. If it still says 403, carry on.

Then open the page yourself in a private browser window, logged out. If you also get "403 Forbidden" or "Access denied", the block hits everyone and it's a settings problem, not a bot problem. Jump to Step 3.

Step 2: find the layer that said no

The 403 page itself usually signs its name. Open the page in a private window, or look at what Google saw under View tested page → HTML, and look for:

  • Cloudflare: "Sorry, you have been blocked", a Ray ID at the bottom, or the response header server: cloudflare.
  • Your host's firewall: a plain page with the host's name, or "Mod_Security" / "Not Acceptable".
  • A WordPress security plugin (Wordfence, iThemes/Solid Security, All In One WP Security): a page naming the plugin, or "Your access to this site has been limited".
  • The web server itself: a bare "403 Forbidden" with "nginx" or "Apache" under it. That's file permissions or a rule in the server's config.

To see the headers yourself, run this in a terminal (Mac, Linux or Windows 10 and later; on Windows type curl.exe instead of curl). Change the address to yours:

curl -sIL https://www.example.com/the-page/

Look at the first line of each block for the code, and at server: for who answered. No terminal: any online "HTTP header checker" shows the same lines.

Step 3: fix it at that layer

Cloudflare

  1. In the dashboard, open your site, then Security → Events. Filter by the page address. Each blocked request shows which rule blocked it.
  2. If the visitor was a verified Google crawler, Cloudflare labels it as a known bot. A custom rule that blocks "all bots", or blocks a country, or challenges every visitor, catches it anyway.
  3. Edit that rule so it skips known bots: in the rule's expression, add Known Bots equals off, or add a separate skip rule above it for verified bots.

Cloudflare's "Under Attack" mode and "Bot Fight Mode" are the usual suspects when a site suddenly gets this status after a scare. Turn them off and run the live test again.

A WordPress security plugin

  1. Open the plugin's log of blocked visitors and search for "Googlebot".
  2. If you see blocks, find the setting that verifies crawlers. The name differs by plugin and version: look under its firewall or blocking options for crawlers or search engines, and make sure it checks real crawlers by address instead of blocking by name.
  3. Remove any country block that covers the United States: most Googlebot visits come from US addresses.

Your host

Shared hosts run their own firewall that you can't see. Send their support the page address, the time Google tried (URL Inspection shows the last crawl time), and ask them to check their firewall log for Googlebot. Ask them to allow Google's published crawler addresses rather than one IP.

A password or a members-only area

If the page is meant to be private (a client area, a staging copy, an account page), the 403 is correct. Google will stop asking about it over time. Stop it showing up in the report by removing it from your sitemap and from links on public pages. If the page should be public, remove the password or the "members only" setting.

The web server

A bare nginx or Apache 403 on everyone usually means the folder has no index page and directory listing is off, or the files can't be read. Ask whoever set up the server, or your host, to check file permissions on that folder.

Step 4: tell Google it's fixed

  1. Run Test live URL again on the example address. It should now show a 200.
  2. Back in Indexing → Pages, open the 403 row and click Validate fix. Google rechecks the listed pages over the next days.
  3. Check a few days later. Pages that pass move to "Indexed" or to another status with its own reason.

What I don't know

My reading was 101 home pages of very large sites, from one server, on one day. It shows how firewalls treat a fake crawler. It doesn't show how often small business sites block the real one: I can't test that, because only Google can send a real Googlebot request. If your site answers 403 to Google and you can't find the rule, the firewall log at Step 3 is the place that knows.

Sources: Google's HTTP status codes and Google Search, Verifying Googlebot and other Google crawlers, and Page indexing report help.
