"Excluded by 'noindex' tag" in Search Console: what it means and how to fix it

24 Oct 2026

One ticked box in WordPress tells Google to skip every page. Check it before anything else.

"Excluded by 'noindex' tag" means Google visited your page and found an instruction on it that says "don't put me in search results". Google obeyed. The page isn't broken and Google isn't punishing you. Something on your site asked it to stay away, and the fix is to find that something and remove it, if you want the page in Google.

On 17 October I fetched the home page of 191 small business websites from a business directory and looked for that instruction. 186 home pages loaded. 4 of them told search engines not to index them, all with the same tag: <meta name='robots' content='noindex, nofollow'>. All 4 run WordPress (versions from 5.3 to 7.1). One was still titled "Just another WordPress site". One also had Google's own Site Kit plugin installed, so its owner had connected it to Google and was presumably waiting for visitors. The same 4 had the same tag when I fetched them on 13 October, so it wasn't a passing state.

That exact tag is what WordPress prints when one checkbox is ticked. Below is that checkbox, the other places a noindex can come from, and how to check and fix each one.

The words, translated

  • Index: Google's list of pages it can show in results. A page that isn't in the index can't be found on Google, however good it is.
  • noindex: an instruction that says "leave this page out of the index". It can sit in the page's HTML as a robots meta tag, or in an X-Robots-Tag header the server sends with the page. Google treats both the same.
  • nofollow: a separate instruction, "don't follow the links on this page". It doesn't remove the page. On my 191 sites, one sent an X-Robots-Tag: nofollow header with no noindex; that page can still be indexed.

Cause 1: WordPress's "Discourage search engines" box

In WordPress, go to Settings → Reading. Near the bottom, under "Search engine visibility" (or "Site visibility"), there's a box labelled Discourage search engines from indexing this site. When it's ticked, WordPress adds noindex, nofollow to every page. I read this in WordPress's own code: the function wp_robots_no_robots() sets noindex, and adds nofollow when the site isn't public.

Many builders tick it while the site is under construction and forget it at launch. Some hosts tick it on new installs. The Dashboard shows a reminder, "Search engines discouraged", in the At a Glance box, but it's easy to miss.

The same box switches off two more things. WordPress's built-in sitemap (/wp-sitemap.xml) is turned off when the site isn't public: in WordPress's code, sitemaps_enabled() returns the same setting. Of the 4 noindex sites, 3 answered 404 at /wp-sitemap.xml on 17 October. The fourth served a sitemap from a plugin instead, so it was handing Google a list of pages that each said "don't index me". That's the classic way this status shows up in Search Console: you submit a sitemap, Google visits every page in it, and every one comes back excluded.

What the box does not do: it doesn't block the site in robots.txt. Since WordPress 5.3 the robots.txt only blocks /wp-admin/, and that's exactly what all 4 of those sites served on 17 October. That matters, because Google has to be allowed to visit a page to see its noindex.

Fix: untick the box, click Save Changes, then clear any cache plugin (WP Rocket, LiteSpeed Cache, W3 Total Cache) and your host's cache, or the old tag keeps being served.

Cause 2: an SEO plugin set to noindex

Yoast SEO, Rank Math and All in One SEO can each mark a single page, a whole post type or a whole archive as noindex.

  • One page: edit the page and open the plugin's box under the editor. In Yoast it's the Advanced tab, the question that asks whether search engines may show this page in search results. In Rank Math it's the Advanced tab, Robots Meta.
  • A whole type: Yoast's Settings → Content types, or Rank Math's Titles & Meta. A switch there can noindex every product, every category page or every tag page.

Noindex on tag pages, author pages and search results is often deliberate. If Search Console lists those, leave them. Only fix the pages you want people to find.

Cause 3: a header from the server or a host

If you can't find a tag in the HTML, the instruction may be in a header, which you can't see on the page. Staging copies, password-protected previews and some hosts' temporary addresses send X-Robots-Tag: noindex. So can a security plugin, an .htaccess line, or a rule at Cloudflare.

To see the headers, open Terminal on a Mac (or PowerShell on Windows, typing curl.exe instead of curl) and run:

curl -sIL https://yoursite.com/page/

Look in the last block for a line starting x-robots-tag. If there's no terminal handy: in Chrome, press F12, open the Network tab, reload, click the first row and read the Response Headers.

Find which one it is, in five minutes

  1. In Search Console, open Indexing → Pages, click the row "Excluded by 'noindex' tag" and look at the list. Every page on the site points to cause 1. Only some pages point to cause 2. Pages you never meant to publish (tags, logins, thank-you pages) may need no fix.
  2. Open one listed page in your browser and view its source: Ctrl+U in Chrome or Edge on Windows, ⌘+⌥+U in Chrome on a Mac. Press Ctrl+F (⌘+F) and search for noindex.
  3. If you find noindex, nofollow on a WordPress site, check Settings → Reading first (cause 1). If you find only noindex, or a longer tag with max-image-preview in it, it's usually the SEO plugin (cause 2).
  4. If the source has no noindex, check the headers (cause 3).

You can also paste the source and the headers into the noindex and canonical checker. It lists every tag and header that can keep the page out, and runs in your browser, so nothing you paste is sent anywhere.

After the fix: tell Google

Google only sees the change the next time it visits the page. Its own page on noindex says that for some pages it "may take months for Googlebot to revisit". You don't have to wait that long:

  1. In Search Console, paste the page's address into the search bar at the top (URL Inspection) and click Test live URL. Under "Indexing allowed?" it should now say Yes. If it still says no, the old page is being served from a cache: clear it and test again.
  2. Click Request indexing. Do this for the home page and your most important pages.
  3. If you use the WordPress built-in sitemap, check that /wp-sitemap.xml loads now, and submit it under Indexing → Sitemaps.
  4. Back on the "Excluded by 'noindex' tag" row, click Validate fix so Google rechecks the rest. Only do this if every page in that row should be indexed: if the row also holds pages you keep out on purpose, validation stops at the first one and fails.

On a new site of mine, pages I requested this way were crawled within minutes and indexed the same day. That's one small site, not a promise.

When noindex is right

Not every page belongs in Google. Thank-you pages after a form, cart and checkout pages, login pages, internal search results and staging copies are better left out. Keep the noindex there and ignore those rows in Search Console. They don't hurt the rest of the site.

One thing not to do: don't block a page in robots.txt to "help" the noindex. Google's own help says the page "must not be blocked by a robots.txt file", because a blocked page is never read, so Google never sees the noindex, and the address can still show up in results if other pages link to it.
