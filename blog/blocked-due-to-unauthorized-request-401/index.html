"Blocked due to unauthorized request (401)" in Search Console: what it means, and how to fix it

5 Nov 2026

A 401 means "log in first". Google never logs in. Either the page should be public, or Google should never have heard of it.

"Blocked due to unauthorized request (401)" is a Search Console status. In plain words: Google asked your server for a page, and the server answered 401 Unauthorized, which means "log in first". Google doesn't log in. Its HTTP status page says it doesn't index URLs that return a 4xx code, and that URLs already indexed are removed when they start returning one.

On 1 November I asked 101 of the most visited domains (the public Tranco top list) for three addresses each: /wp-admin/, /admin/ and /api/. That's where you'd expect logins. 216 of the requests got an answer, following redirects to the end. Exactly one ended in a 401: t.me/api/. The admin paths mostly ended in 404 (32 for /admin/) or 200 (28), with a handful of 403s.

That 200 is the part to notice. Big sites send you to a login page, and the login page itself answers 200. A real 401 means the server is asking for a password before showing anything at all. On a public site that is unusual, so when Google reports it, the cause is almost always one of three things below.

The words, translated

  • 401 Unauthorized: the server wants credentials, and says how in a header called WWW-Authenticate. In a browser this is the grey pop-up box asking for a username and password, not a login form on a page.
  • 403 Forbidden: the near twin. The server knows what you want and refuses it, login or not. That has its own status and its own post.
  • Basic auth (HTTP authentication): the simplest way to put a password on a whole site or folder, often used to hide a staging copy. It is the most common source of a 401.
  • Staging site: a private copy of your site where changes are tried before going live, often at an address like staging.example.com.

The three usual causes

  1. A staging or preview address got out. A link in a page, a sitemap built on the staging copy and uploaded to the live site, or a canonical tag still pointing at staging. Google follows it, meets the password, and reports a 401.
  2. The whole live site still has a password. The site launched, but the basic auth from the build phase was never removed, or a host's "password protect this site" switch is still on. Every page in the report, home page included, is the sign.
  3. A private area is linked from a public page. An account page, a client folder or an API address that should stay private, but sits in your menu, footer or sitemap.

The fix is opposite for the first two and the third. If the page should be public, remove the password. If it should stay private, keep the 401 and stop telling Google about the address.

Step 1: see what Google sees

  1. In Search Console, open Indexing → Pages, click the "Blocked due to unauthorized request (401)" row, and look at the example addresses. Note the host name: is it your live address, or a staging or preview one?
  2. Paste one example into the search bar at the top (URL Inspection) and press Enter.
  3. Under Page indexing, look at Referring page and Sitemaps. They tell you where Google found the address. That is often the whole answer.
  4. Click Test live URL to see whether it still answers 401 now.

Step 2: check the answer yourself

Open the address in a private browser window. A grey pop-up asking for a username and password is basic auth. A normal login page with your site's design is not a 401 at all: check the address again, because Google may have seen something different.

For the exact answer, run this in a terminal (Mac, Linux or Windows 10 and later; on Windows type curl.exe). Change the address to yours:

curl -sIL https://staging.example.com/the-page/

Keep the -L. Without it you only see the first hop. In my reading the first pass without it showed mostly 301 and 302 redirects, which say nothing about where you end up. Read the first line of the last block for the final code, and look for a www-authenticate: line. www-authenticate: Basic realm="..." means basic auth, set in the web server or by the host.

Step 3: fix it

The page should be public: remove the password

  • Apache: look in the site's .htaccess for lines starting AuthType Basic, AuthName, AuthUserFile and Require valid-user. Remove them, or ask your host to.
  • nginx: look in the site's config for auth_basic and auth_basic_user_file, remove them, and reload nginx.
  • A host's switch: many hosts and site builders have a "password protect" or "site protection" setting for the whole site. The name differs by host. Turn it off for the live site.

Then open the page in a private window. No pop-up means it's fixed.

The page should stay private: stop pointing Google at it

  1. Remove the address from your sitemap. If the sitemap was generated on staging, regenerate it on the live site, and open it to check every address starts with your live host.
  2. Remove links to it from public pages. The "Referring page" from Step 1 tells you which one.
  3. Check the canonical tag on your live pages. In the page source, search for rel="canonical". It should point to the live address, never staging.

Keep the password. It is doing its job. Google will stop asking over time, and the row will shrink on its own.

Don't swap the password for a noindex tag on staging. Google can't read a tag on a page it can't open, and removing the password to let it read the tag shows your staging copy to everyone.

Step 4: tell Google

  1. If you removed a password, run Test live URL on an example. It should show a 200. Click Request indexing, then go back to the 401 row and click Validate fix.
  2. If the pages are meant to stay private, don't validate. Validation checks each page and would fail on a page that still answers 401 on purpose.

What I don't know

My reading was 3 addresses on each of 101 very large sites, from one server, on one day, and 29 of the domains didn't answer at all. It shows that a 401 is rare on public addresses. It doesn't show how often small sites leave a staging password on after launch. If your report lists only a few addresses on a staging host, it is the first cause. If it lists your home page, it is the second.
