"Redirect error" is a Search Console status. In plain words: Google asked for one of your pages, your server said "not here, go there", and Google followed, but never arrived at a real page. Google's Page indexing help lists the causes: "A redirect chain that was too long", "A redirect loop", "A redirect URL that eventually exceeded the max URL length", and "A bad or empty URL in the redirect chain". The page stays out of Google until the redirect is fixed.

On 21 October I asked 191 small business websites from a business directory for their home page four ways: with and without www, over https and plain http. That's 764 requests, each one following up to 10 redirects, the same limit Google uses. 733 got an answer, and 16 of the other 31 answered when I asked again a few minutes later. None of them looped. The longest chain was 4 hops. But 90 of the 191 sites made at least one of their four addresses take 2 or more hops, and 3 sites sent visitors from the secure https address back to plain http.

So a real redirect error is rare on a home page. Long-ish chains are common, and they're the setup that turns into an error the day someone adds one more rule. Below is how to read the status, how to trace your own redirects, and how to fix each case.

The words, translated

  • Redirect: the server answering "this page moved, go to this other address" instead of sending the page. The answer has a code starting with 3: 301 and 308 mean moved for good, 302 and 307 mean moved for now.
  • Hop: one redirect. Going from http://www.yoursite.com/ to https://www.yoursite.com/ is one hop.
  • Chain: several hops in a row before the real page. Google's crawler docs: "Googlebot generally follows 10 redirect hops when crawling for general web content." After 10, it gives up.
  • Loop: a chain that comes back to where it started, so it never ends. In a browser this shows as "This page isn't working: redirected you too many times" (ERR_TOO_MANY_REDIRECTS).

Don't confuse this status with "Page with redirect". That one means the redirect worked and Google indexed the address it points to. "Redirect error" means it didn't work.

What a chain looks like

The most common 2-hop chain in my reading started at http://www.: 71 of the 105 two-hop answers. Here's one, traced with the command in the next section:

HTTP/1.1 301 Moved Permanently
Location: https://www.example.com/
HTTP/2 301
location: https://example.com/
HTTP/2 200

Step one adds https. Step two drops www. Each rule is fine alone. Together they make two hops where one would do: http://www.example.com/ could go straight to https://example.com/.

The 4-hop chain was worse. It went from http to https, then back to http on the bare address, then to https again, then to a language page:

http://www.example.com/      301  →  https://www.example.com/
https://www.example.com/     308  →  http://example.com/
http://example.com/          301  →  https://example.com/
https://example.com/         302  →  https://example.com/lb/en

That's 4 of Google's 10 hops spent on the home page. It still works. One more redirect on the same page, for a language or a new domain, and it starts to add up.

Trace your own redirects in two minutes

Start in Search Console: Indexing, then Pages, then the "Redirect error" row. The examples list the affected addresses. Copy one.

Open Terminal on a Mac, or Command Prompt on Windows 10 or 11 (type curl.exe instead of curl). Paste this with the address you copied:

curl -sIL --max-redirs 10 https://yoursite.com/the-page/

-I asks for headers only, -L follows each redirect, and --max-redirs 10 stops where Google stops. Read the lines that start with HTTP and Location. Each 3xx plus a Location is one hop. The last HTTP line should say 200.

To count the hops for your four home page addresses at once:

curl -sS -L -o /dev/null -w "%{num_redirects} hops, %{http_code} %{url_effective}\n" http://www.yoursite.com/
curl -sS -L -o /dev/null -w "%{num_redirects} hops, %{http_code} %{url_effective}\n" http://yoursite.com/
curl -sS -L -o /dev/null -w "%{num_redirects} hops, %{http_code} %{url_effective}\n" https://www.yoursite.com/
curl -sS -L -o /dev/null -w "%{num_redirects} hops, %{http_code} %{url_effective}\n" https://yoursite.com/

On Windows, replace /dev/null with NUL. A healthy result: every line ends at the same https address, with 0 or 1 hops.

What the bad results look like:

  • Maximum (10) redirects followed: a loop, or a chain past Google's limit. Run the -sIL command and look for the same Location appearing twice.
  • 2 or more hops: works today. Fix it while it's easy (below).
  • An https line ending at an http:// address: your site sends secure visitors to the insecure version. 3 of the 191 sites did this, each in one hop from the bare https address to http www. Browsers show "Not secure" on the page they land on. See why a site says "Not secure".
  • A last line that isn't 200: the chain ends on an error. In my reading, 4 addresses ended on 500, 3 on 503, 2 on Cloudflare's 525. That's a server error, not a redirect problem.

Don't use the "Test live URL" button for this. Google's own docs say "Google Inspection Tools doesn't follow redirects", so it shows only the first hop.

Fix 1: a loop behind Cloudflare

If your site is on Cloudflare and you see "redirected you too many times", check this first. Cloudflare's troubleshooting page for ERR_TOO_MANY_REDIRECTS explains it: with the encryption mode set to Flexible, "Cloudflare sends unencrypted requests to your origin server over HTTP", and "Redirect loops will occur if your origin server automatically redirects all HTTP requests to HTTPS." Cloudflare asks your server over http, your server says "use https", Cloudflare asks over http again.

  1. In the Cloudflare dashboard, open your domain, then SSL/TLS, then Overview.
  2. If the mode is Flexible and your server has its own certificate (most hosts give one free), change it to Full (strict).
  3. If your server has no certificate, Cloudflare's other fix is to remove the https redirect on your server and let Cloudflare's "Always Use HTTPS" do it instead.
  4. Run the curl lines again.

Fix 2: a loop on WordPress

WordPress builds its redirects from two settings: Settings, then General, then "WordPress Address (URL)" and "Site Address (URL)". If those say https://www.yoursite.com and a rule at your host or in a plugin sends www to the bare address, the two keep sending visitors back and forth.

  1. Decide on one address: with or without www, always https.
  2. Put exactly that address in both WordPress fields.
  3. Check the host's control panel and any redirect or security plugin for a rule that disagrees, and make it match or turn it off.

If the loop locks you out of the dashboard, the two fields can also be set in wp-config.php with WP_HOME and WP_SITEURL. WordPress's wp-config.php reference page shows both.

Fix 3: a chain longer than it needs to be

The goal: every old address goes to the final address in one hop.

  1. Write down the final address. For a home page, that's the line every curl command ended at.
  2. Find where each hop comes from. Usually one is the host ("force https") and one is a www rule (Cloudflare, the host, or WordPress).
  3. Replace them with one rule that sends any http or www address straight to the final https address, path included. In Cloudflare, a single redirect rule can match both http:// and the www name and send them to https://yoursite.com/${1}. My post on www and the bare address has those steps.
  4. If you moved pages, update the old redirects too. A redirect from 2022 that points at an address you've since redirected again is a hidden second hop.
  5. Change internal links and your sitemap to the final addresses, so Google doesn't start on a redirect at all.

After the fix

  1. Run the curl lines again. 0 or 1 hops, ending at 200.
  2. In Search Console, open URL Inspection for the final address and click "Request indexing".
  3. Back on the "Redirect error" row, click "Validate fix". Google's Page indexing help says validation typically takes up to about two weeks.

One thing my reading didn't cover: inner pages. I only checked home pages. An old blog post that went through two site moves gets one hop per move, so trace a few of your oldest addresses too.
