"Indexed, though blocked by robots.txt" means Google put one of your addresses in its results without ever reading the page behind it. Your robots.txt file told Google not to fetch that address, so it didn't. But other pages linked to it, and links are enough for Google to know the address exists and what people call it. So it shows the address, with no real description.

On 31 October I fetched the robots.txt of 101 of the world's most visited domains, from the public Tranco top-sites list, with a normal browser user agent. 45 answered with a real robots.txt file (13 more sent an HTML page instead, 29 didn't answer). Of the 45, 38 told Google not to crawl at least one path. Wikipedia's file has 428 Disallow lines that apply to Google, Vimeo's 330, Amazon's cloud storage domain 266, Pinterest 217, and Google's own 170. Only 2 blocked Google from everything. So blocking some paths is normal, even on the biggest sites. And every one of those blocked paths that someone links to can end up in this row.

That's why the row isn't an error. It's a question Search Console is asking you: do you want this page in Google or not? The fix depends on the answer, and both answers start the same way.

Why Google indexes a page it can't read

robots.txt controls crawling, not indexing. Google's robots.txt guide says it plainly: a page disallowed in robots.txt "can still be indexed if linked to from other sites", and such a result "won't have a description". The same guide warns: "Don't use a robots.txt file as a means to hide your web pages ... from Google Search results."

Picture it from Google's side. A link on some page points to yoursite.com/members/price-list. Google wants to read it, checks your robots.txt, sees Disallow: /members/, and stops at the door. It still has the link, and the words in it. If enough pages point there, it can list the address, titled from those link words, with nothing underneath.

Step 1: list the pages and sort them

  1. In Search Console, open Indexing, then Pages, and click the Indexed, though blocked by robots.txt row.
  2. Read the example URLs. For each, answer one question: would I want a stranger to land on this page from Google?
  3. Put the yes pages in one pile (a service page, a product, a blog post, a PDF menu) and the no pages in another (cart, checkout, account, login, admin, internal search results like ?s= or /search?q=, filter and sort links, staging copies, private files).

Most sites have only no pages here, and they arrive in a few familiar shapes: search result pages someone linked to, tag or filter pages with tracking parameters, and old private folders that a forum or a partner linked years ago.

Step 2: confirm which line blocks it

Don't guess from a long file. Open https://yoursite.com/robots.txt on the exact host in the URL (with or without www, each has its own file), find the group Google uses, and find the Disallow line whose path the URL starts with. If you'd rather not read rules by hand, paste the file and the URL into the robots.txt tester, which names the line. The full walk-through, with the common platform defaults, is in my post on the "Blocked by robots.txt" row.

Also check who wrote the line. On Shopify the defaults come from the platform's template, on WordPress an SEO plugin or a privacy setting may add lines, and Cloudflare can add a managed block on top of your file. Change the line where it's made, or it comes back.

Fix A: you want the page in Google

  1. Remove or narrow the Disallow line that matches it. If the line blocks a whole folder you want mostly kept out, add a more specific Allow: line for the one page. Google follows the longest matching rule.
  2. Open the robots.txt in a private window to confirm the live file changed. A cache or CDN can serve the old one for a while.
  3. In Search Console, paste the URL into the search bar at the top (URL Inspection), click Test live URL, and check that crawling is now allowed. Then click Request indexing.

Once Google can read the page, the result gets its real title and description, and the URL moves to the normal indexed list.

Fix B: you want the page out of Google

This is where most people go wrong, because the instinct is to block harder. A stricter robots.txt can't help: Google already isn't reading the page. To get it out, Google has to read it once more and find a clear "don't index me". The order that works:

  1. Unblock it first. Remove the Disallow line that matches the page. Yes, for a page you want gone.
  2. Add noindex. Put <meta name="robots" content="noindex"> in the page's <head>. For a PDF or other file without HTML, send the header X-Robots-Tag: noindex instead. Or, if the page shouldn't exist for the public at all, put it behind a password or delete it so it answers 404.
  3. Let Google crawl it. Request indexing in URL Inspection to speed it up. Google reads the noindex and drops the page.
  4. Only then block it again, if you need to save crawling, and only once it's gone from the report. Re-blocking too early freezes it in place.

If you need it hidden today, Search Console's Removals tool hides a URL from results for about six months. It's a bandage: the page comes back if the cause is still there.

The noindex trap

The most common stuck case looks like this: the page has a noindex tag and a robots.txt block at the same time. It feels doubly safe. It is the one combination that never works, because the block stops Google from seeing the tag. The page stays "Indexed, though blocked" for months.

To check a page for it, open its source (Ctrl+U on Windows, Cmd+Option+U in Chrome on a Mac) and search for noindex. If it's there and the URL also matches a Disallow line, pick one: for a page you want out of Google, keep the noindex and remove the block.

When to leave the row alone

If every URL in the row is a no page, nobody is likely to search for it, and it isn't private, you can leave it. A cart page shown as a bare address hurts nobody. Don't press Validate fix on a row you're keeping on purpose: the pages are still blocked, so the check fails.

Do act when a listed URL holds something private (a price list, a client folder, an invoice, a staging copy). robots.txt was never protection: it's a public file anyone can read, and it lists the very paths you meant to hide. Put those pages behind a password, then follow Fix B.

The short version

  • The row means Google knows the address from links but never read the page.
  • Sort each URL: in Google or out of it.
  • In: remove the Disallow line, test the live URL, request indexing.
  • Out: remove the Disallow line, add noindex (or a password, or a 404), let Google crawl it, and only re-block once it's gone.
  • Never pair noindex with a robots.txt block. Google can't see the tag through the block.
