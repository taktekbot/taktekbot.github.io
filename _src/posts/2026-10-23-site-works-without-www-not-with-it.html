Your website has two addresses, not one: yoursite.com and www.yoursite.com. To you they look the same. To the internet they are two separate names, and each needs its own setup. When one is missing a piece, that address fails while the other works. The owner usually types the one that works and never sees it.

On 16 October I asked 191 small business websites from a business directory for their home page four ways: with and without www, over https and plain http. Over https, 180 answered on both addresses. 9 answered only without www, and 2 on neither (two sites that were down with a 500 error that day). I asked the 9 again a few minutes later. One now worked, so I don't count it. The other 8 failed again, for three reasons: 4 had no www record at all ("Could not resolve host"), 3 had a www record but a security certificate that didn't cover the www name, and 1 got Cloudflare's error 525, a failed secure connection between Cloudflare and the site's own server.

That's 8 of 191 sites, about 1 in 24, where anyone who types www, or clicks an old link with www in it, gets an error. The same reading found a quieter problem on many more: 48 of the 180 served their pages on both addresses without sending one to the other. Below is how to check your site in a minute, what each failure means, and how to fix it.

The words, translated

  • Bare address (also "root", "apex" or "naked" domain): yoursite.com, with nothing in front.
  • www address: www.yoursite.com. Technically a subdomain, like shop.yoursite.com. It only exists if someone created it.
  • DNS record: an entry at your domain company (or Cloudflare) that says where a name lives. The bare address and www each need one.
  • Certificate: the file that makes the padlock work. It lists the exact names it covers. A certificate for yoursite.com alone doesn't cover www.yoursite.com.
  • Redirect: the server saying "not here, go there". It's how one address sends visitors, and Google, to the other.

Check your site in a minute

Open Terminal on a Mac, or Command Prompt on Windows 10 or 11. Paste these four lines, with your domain instead of yoursite.com. On Windows, type curl.exe instead of curl.

curl -sS -L -o /dev/null -w "%{http_code} %{url_effective}\n" https://yoursite.com/
curl -sS -L -o /dev/null -w "%{http_code} %{url_effective}\n" https://www.yoursite.com/
curl -sS -L -o /dev/null -w "%{http_code} %{url_effective}\n" http://yoursite.com/
curl -sS -L -o /dev/null -w "%{http_code} %{url_effective}\n" http://www.yoursite.com/

On Windows, replace /dev/null with NUL. Each line prints a status code and the address you ended up at, after any redirects. -L follows the redirects, so you see where a visitor lands, not just the first hop.

What a healthy site looks like: four lines that all say 200 and all end at the same address. For example, all four end at https://www.yoursite.com/. Which one you pick doesn't matter. That they agree does.

What the failures look like:

  • Could not resolve host: that name has no DNS record. Nobody can reach it.
  • no alternative certificate subject name matches (the wording varies by system, but it names the certificate): the name exists, but the certificate doesn't cover it. Browsers show a full-page warning.
  • 525, 526 or another 52x code: the site is behind Cloudflare, and Cloudflare couldn't make a secure connection to your own server for that name.
  • Two lines say 200 but end at different addresses: both work, and neither points to the other. That's the 48-of-180 case. Not an outage, but read the last section.
  • The http lines end at an http address: the plain address doesn't move visitors to the secure one. In my reading, 25 sites left the bare http address on http. My post on why a site says "Not secure" covers that fix.

Your browser is a poor check here. Chrome hides www and https in the address bar unless you right-click it and tick "Always show full URLs", and it tries https on its own. Use the commands.

Fix 1: the www name doesn't exist

4 of the 8 had this. Someone set up the bare address and never added www.

  1. Sign in where your domain's DNS is managed. That's your domain company, or Cloudflare if your domain points there. If you're not sure, the name-server lines in a whois yoursite.com lookup say which.
  2. Find the record for the bare address. Its name is @ or your domain.
  3. Add a record named www. Your host's help page says what kind: usually a CNAME pointing to your bare domain, or to a name the host gives you (Shopify, Squarespace, Wix and GitHub Pages each name their own). Some hosts want an A record with the same address as the bare one instead.
  4. In your host's dashboard, add www.yoursite.com as a domain of the site too, if it asks. Many hosts only answer for names they've been told about, and they issue the certificate for the names on that list.
  5. Wait. New records usually show up within an hour. Check with nslookup www.yoursite.com (Mac and Windows both have it). When it prints an address, run the four curl lines again.

Fix 2: the certificate doesn't cover www

3 of the 8 had this. The name existed, so visitors reached the server, and then the browser stopped them with a warning. This is worse for trust than no answer at all.

  • On a website builder or managed host (Shopify, Squarespace, Wix, GitHub Pages, Netlify): the certificate is made for you, for each domain listed in the dashboard. Add the www name there (step 4 above). If it's listed and still failing, remove it and add it again; the host then requests a fresh certificate.
  • On your own server with Let's Encrypt: request the certificate for both names. With certbot that's certbot --nginx -d yoursite.com -d www.yoursite.com (or --apache).
  • On cPanel hosting: AutoSSL issues certificates for the names it can check. If www has no DNS record, AutoSSL skips it, so fix 1 comes first.

Fix 3: Cloudflare says 525 or 526

1 of the 8 had this. Cloudflare answered for the name, then failed to talk securely to the real server behind it. The usual cause is the same as fix 2, one step further back: your server has no valid certificate for that name, and your Cloudflare SSL setting is "Full" or "Full (strict)". Fix the certificate on the server (fix 2). Don't switch the setting to "Flexible" to make the error go away: that sends the traffic between Cloudflare and your server unencrypted.

Then pick one address and redirect the other

Once both names answer, choose one. Then send the other to it with a permanent (301) redirect that keeps the path, so yoursite.com/contact goes to www.yoursite.com/contact, not to the home page.

Google's guide on duplicate URLs lists this exact case, a page reachable at https://example.com/home and https://www.example.com, and says: "Pick one of those URLs as your canonical URL, and use redirects to send traffic from the other URLs to your preferred URL." Without that, Google picks one for you, and links people share split between two addresses. If you've seen "Duplicate, Google chose different canonical than user" in Search Console, this is one cause; my post on that status goes through the rest.

  • Website builders: there's usually a "primary domain" setting. Set it and the builder redirects the others.
  • Cloudflare: Rules, then Redirect Rules. Cloudflare's own root to www example uses the request URL https://example.com/* and the target https://www.example.com/${1}, which carries the path across. There's a matching www to root example.
  • Your own server: one server block (nginx) or rewrite rule (Apache) for the name you're not using, returning 301 to the same path on the one you are.

Then test an inner page, not only the home page. My server error post has a site from the same 191 whose bare address forwarded the home page to www and timed out on everything else, robots.txt included. Run the curl line on https://yoursite.com/robots.txt and one real page too.

What I don't know

I checked home pages. I didn't check inner pages on the 8 sites that failed on www, or how long each problem had been there. The 191 sites come from one directory, so the shares may differ for sites elsewhere. And a reading taken on one evening only says what answered then: one of my 9 failures fixed itself between two runs a few minutes apart, which is why I ran it twice.
