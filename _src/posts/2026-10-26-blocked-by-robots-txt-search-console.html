"Blocked by robots.txt" means Google found a link to one of your pages but didn't open it, because your robots.txt file told it not to. robots.txt is a small text file at the root of your site (yoursite.com/robots.txt) that crawlers read before anything else. A line like Disallow: /checkout in it means "don't fetch anything whose address starts with /checkout". Google obeyed. Whether that's a problem depends entirely on which pages are on the list.

On 19 October I fetched the robots.txt of 191 small business websites from a business directory, twice, five hours apart, with the same result both times. 154 answered with a file. None of the 154 blocked the whole site for Google: no Disallow: / under User-agent: * or under Googlebot. 5 files did contain Disallow: /, and all 5 aimed it at other bots by name: one blocked 80 AI crawlers in a single group (GPTBot, ClaudeBot, Google-Extended, PerplexityBot and more), the other 4 blocked SEO tools' crawlers such as SemrushBot, MJ12bot and DotBot. Most rules were ordinary: 57 files disallowed /wp-admin/, the WordPress default, and 34 carried Shopify's default set (/checkouts/, /orders, /cdn/wpm/*.js, with /checkout in 40). Just 1 blocked the folders WordPress loads its styles and scripts from.

So on real small sites the whole-site block is rare, and the blocked rows Search Console shows are mostly cart, account and admin pages that the platform blocks for you. Below is how to tell which kind you have.

The two rows, translated

  • Blocked by robots.txt. In the "Why pages aren't indexed" table of the Page indexing report. Google didn't crawl the page and didn't index it. Usually fine.
  • Indexed, though blocked by robots.txt. The page is in Google even though Google never read it. Google's robots.txt guide says why: "A page that's disallowed in robots.txt can still be indexed if linked to from other sites." The result shows your address and maybe the words other sites used to link to it, but no real description, because Google never saw the page.

The second one surprises people, and it comes from a common mix-up. robots.txt controls crawling, not indexing. Google's own warning on the same page: "Don't use a robots.txt file as a means to hide your web pages ... from Google Search results." If you want a page out of Google, use noindex or a password, and don't block it in robots.txt, or Google can't see the noindex. My earlier post on whether a small site needs a robots.txt covers that mistake in more detail.

Step 1: look at which pages are listed

  1. In Search Console, open Indexing, then Pages.
  2. Under "Why pages aren't indexed", click Blocked by robots.txt.
  3. Read the example URLs. Sort them into two piles: pages you'd want a stranger to find from Google (a service page, a product, a blog post), and everything else (cart, checkout, account, login, admin, search results, filter and sort links with ? in them).

If every URL is in the second pile, you're done. Those pages have no business in search results, and blocking them is the platform working as designed. Don't press "Validate fix" on this row: there is nothing to fix, and the blocked pages will stay blocked.

Step 2: find the line that blocks a page you want

For a page from the first pile, find the exact rule. Guessing from a long file is how people delete the wrong line.

  1. Open https://yoursite.com/robots.txt in a browser. Use the exact host Google uses, with or without www: each host has its own robots.txt.
  2. Find the group that applies to Google. A group starts with one or more User-agent: lines. Google uses the group that names it most specifically (Googlebot), and only falls back to User-agent: * when no group names it. If a Googlebot group exists, the * rules don't apply to Google at all.
  3. In that group, compare each Disallow: and Allow: path with the start of your page's path. The longest matching rule wins; on a tie, Google picks the less restrictive one, so Allow beats Disallow. * matches any characters and $ means "the address ends here".

Or paste the file and the URL into my free robots.txt tester: it runs in your browser and shows the line that decided each URL. In Search Console itself, the URL Inspection tool tells you whether crawling is allowed for one URL, and Settings, then robots.txt, shows the file Google last fetched and when.

Three causes I'd check first:

  • A rule that's too short. Disallow: /p blocks /products/, /pricing and /portfolio, because rules match the start of the path. Add the trailing slash or the full folder name.
  • A leftover from building the site. Some sites block everything while they're being built and the line survives launch. In WordPress, the "Discourage search engines" checkbox doesn't do this through robots.txt in current versions: it adds a noindex tag instead (covered in the noindex post). An SEO plugin or a hand-edited file can.
  • A rule meant for another bot. In the 5 files from my reading that used Disallow: /, the rule sat in a group for named bots, which is fine. Move it under User-agent: * by accident, or delete the User-agent: line above it, and it blocks Google too.

Step 3: fix it

  1. Remove or narrow the rule. On WordPress, a plugin such as Yoast or Rank Math usually writes the file, so edit it there; a real robots.txt file in the site's root folder overrides the one WordPress generates. On Shopify the file is the theme's robots.txt.liquid template.
  2. Check the live file again, on both www and the bare domain.
  3. Run URL Inspection on the page, then Request indexing. Once crawling is allowed, Google can read the page and decide on it like any other.
  4. Then press Validate fix on the row, if every URL you care about is now allowed. If the row also holds cart and account pages, validation will keep finding those blocked, so skip it and watch your pages one by one instead.

"Indexed, though blocked": two different fixes

It depends on what you want for that page.

  • You want it in Google. Remove the blocking rule, as above. Once Google can crawl it, the result gets a proper title and description.
  • You want it out of Google. This is the order that works: first remove the robots.txt rule, then add <meta name="robots" content="noindex"> to the page (or an X-Robots-Tag: noindex header for PDFs), then let Google crawl it. Google has to read the page to see the noindex. Keep the page crawlable. For a quick removal while you wait, Search Console's Removals tool hides a URL for about six months, but it doesn't remove it for good.

Don't block your styles and scripts

One file in my reading disallowed the WordPress folders that hold the theme's CSS and JavaScript. Google renders pages much like a browser does, and its guide says that if missing files "make the page harder for Google's crawler to understand the page, don't block them". A page Google sees without its styles can look broken or empty to it. If your file has Disallow: /wp-content/ or Disallow: /wp-includes/, or a rule that covers your .css and .js files, remove it. Blocking /wp-admin/ is fine; WordPress's own default file does that and allows admin-ajax.php.

If your robots.txt doesn't load at all

30 of the 191 sites answered 404 for robots.txt in my reading. That's fine: Google treats a missing file as "crawl everything". An error is different. When robots.txt answers with a 5xx code, Google's spec says it stops crawling the whole site for the first 12 hours, then falls back to the last copy it fetched. That case has its own post: Server error (5xx) in Search Console.

The short version

  • "Blocked by robots.txt" is usually your platform keeping cart, checkout and admin pages out. Read the example URLs before changing anything.
  • For a page you want found, find the exact line, in the group Google actually uses, and narrow or remove it.
  • robots.txt stops crawling, not indexing. To keep a page out of Google, allow crawling and use noindex.
  • Never block the folders your CSS and JavaScript load from.

Sources: Google's introduction to robots.txt (the quotes above) and how Google interprets the robots.txt specification.
