If go test ./store passes, go test ./api passes, but go test ./... fails, the usual cause is this: Go runs the tests of different packages at the same time, and your packages share something. Most often it's one test database.

One package deletes rows while another is still reading them. Neither test is wrong. They just run in parallel against the same tables.

Here is how to confirm it in one command, and how to fix it properly.

Why it happens

Each package's tests are compiled into their own test binary. go test ./... runs several of those binaries at once. The go help build text for the -p flag says it plainly: it's "the number of programs, such as build commands or test binaries, that can be run in parallel. The default is GOMAXPROCS, normally the number of CPUs available."

This is separate from t.Parallel(). You can have zero t.Parallel() calls in your code and still have packages running side by side. The -parallel flag only works inside one binary; go help testflag notes that tests for different packages may run in parallel too, according to -p.

The failures look random. They change with how fast your machine is and which packages finish compiling first. That's the giveaway: a test that fails "sometimes", only in the full run, and never alone.

Step 1: confirm it in one command

Run the whole suite again, one package at a time, with the cache off:

go test -p 1 -count=1 ./...
  • -p 1 runs one test binary at a time.
  • -count=1 turns off the test cache. The Go docs call it "the idiomatic way to disable test caching explicitly". Without it, a package that passed before prints (cached) and never touches the database, which can hide the problem or make it look fixed.

If this passes and plain go test -count=1 ./... fails, your packages are sharing something. If both fail, the bug is somewhere else: look at the test itself.

Step 2: find what they share

A database is the most common one, but check the whole list:

  • A database: same name, same tables, setup code that truncates or drops them.
  • A fixed port: two packages both start a test server on :8080. One of them gets "address already in use".
  • A fixed file path: both write /tmp/test.db or testdata/out.json.
  • An outside service: the same Redis database, the same bucket, the same queue name.

Search your test helpers for hard-coded names: grep -rn "TRUNCATE\|DROP TABLE\|:8080\|/tmp/" --include=*_test.go . is a quick start.

Step 3: give each package its own database

The tempting fix is to put -p 1 in your Makefile or CI and move on. It works, and it makes the suite slower with every package you add. It also leaves a trap for the next person who types plain go test ./....

The real fix is to stop sharing. In each package that needs a database, create a fresh one in TestMain, run your migrations into it, and drop it at the end. A sketch for PostgreSQL with database/sql:

package store

import (
	"database/sql"
	"fmt"
	"log"
	"net/url"
	"os"
	"testing"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

var testDB *sql.DB

func TestMain(m *testing.M) {
	// e.g. postgres://user:pass@localhost:5432/postgres
	adminURL := os.Getenv("TEST_DATABASE_URL")
	admin, err := sql.Open("pgx", adminURL)
	if err != nil {
		log.Fatal(err)
	}
	defer admin.Close()

	// A unique name per run, so packages never meet.
	name := fmt.Sprintf("test_store_%d", time.Now().UnixNano())
	if _, err := admin.Exec("CREATE DATABASE " + name); err != nil {
		log.Fatal(err)
	}
	defer admin.Exec("DROP DATABASE IF EXISTS " + name + " WITH (FORCE)")

	u, _ := url.Parse(adminURL)
	u.Path = "/" + name
	testDB, err = sql.Open("pgx", u.String())
	if err != nil {
		log.Fatal(err)
	}
	defer testDB.Close()

	if err := migrate(testDB); err != nil { // your own migration step
		log.Fatal(err)
	}
	m.Run()
}

Three details matter here:

  1. Don't call os.Exit(m.Run()) if you rely on defer. os.Exit skips deferred calls, so the database would never be dropped. Since Go 1.15, the testing docs say that if TestMain returns, the wrapper passes m.Run's result to os.Exit itself. Just call m.Run() and return.
  2. Defers run last-in, first-out, so testDB.Close() runs before the DROP. WITH (FORCE) drops the database even if a stray connection is still open; it needs PostgreSQL 13 or newer (docs).
  3. Prefix the names with test_. A crashed or killed run can't clean up after itself. With a prefix, you can list and drop the leftovers in one query.

Move this into a small shared helper (for example an internal/testdb package with a New(prefix) function) so every package does it the same way.

If you use SQLite

It's simpler: give each package its own file. t.TempDir() isn't available in TestMain, so use os.MkdirTemp("", "store-test-"), open test.db inside it, and remove the folder at the end. Or open the database per test with filepath.Join(t.TempDir(), "test.db"), and Go removes it for you.

Step 4: fix the other shared things

  • Ports: use httptest.NewServer, or listen on 127.0.0.1:0 and read the port the system picked.
  • Files: write under t.TempDir(), never a fixed path.
  • Environment variables: set them with t.Setenv, which restores the old value when the test ends.
  • Outside services: put a unique prefix on every key, bucket or queue name, the same way as the database name.

Inside one package, the same rule applies

A database per package stops packages fighting. Tests inside one package can still fight if they call t.Parallel(). There, the usual fixes are to give each test its own rows (unique emails, unique IDs) instead of truncating tables, or to run each test inside a transaction you roll back at the end.

Checklist

  1. Run go test -p 1 -count=1 ./.... If it passes, packages share something.
  2. Find the shared database, port, file or service.
  3. Create a uniquely named database per package in TestMain; drop it with defer, and don't call os.Exit.
  4. Use httptest, port 0, t.TempDir() and t.Setenv for the rest.
  5. Run plain go test -count=1 ./... a few times in a row. It should pass every time.
