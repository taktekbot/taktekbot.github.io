"Server error (5xx)" is a Search Console status. In plain words: Google asked your site for a page and your server answered with an error instead of the page. The error codes all start with 5: 500, 502, 503, 522 and so on. Google's Page indexing help says only this: "Your server returned a 500-level error when the page was requested."

On 16 October I asked 191 small business websites from a business directory for two things: their home page, and their robots.txt, the small file Google reads before it crawls anything. 189 home pages answered 200, fine. 2 answered 500. One of them served a page titled "Server Error"; the other sent back 107 bytes. Both did the same when I asked again a minute later.

The robots.txt check found something the home page check missed. One site's home page answered 200 in 0.7 seconds, twice. Its robots.txt answered 522 after about 20 seconds, twice. 522 is Cloudflare's code for "Cloudflare timed out contacting the origin web server", meaning the site's own server never answered. Looking closer: the address without www forwards only the home page to the www version. Every other address without www (robots.txt, /about) times out, while the same addresses with www answer 200 in half a second. The owner types the name, lands on the home page and sees nothing wrong. Google asks that host for robots.txt first and gets an error. The other site with a 500 home page also answered 500 for its robots.txt.

That second finding is the reason to read on even if your home page loads. Here's what Google does with each case, how to check your own site, and the usual fixes.

The words, translated

  • Status code is a three-digit number your site sends before every page. People never see it. Google reads it first. 200 means "here's the page". 404 means "no page here".
  • 5xx means "the server failed". Not "the page is gone" (that's 404), but "something broke while making it". 500 is a general crash, often a code or plugin error. 502 and 504 mean one server waited on another and gave up. 503 means "unavailable right now, come back later". 520 to 527 are Cloudflare's own codes for "your server didn't answer me properly".
  • robots.txt is a plain text file at yoursite.com/robots.txt. It tells crawlers what they may read. Most sites don't need much in it. But Google asks for it before crawling, and what your server answers there matters for the whole site.

What Google does with a 5xx

Google's guide to HTTP status codes is short and clear on this:

  • It slows down: "5xx and 429 server errors prompt Google's crawlers to temporarily slow down with crawling." For a 500, "the decrease in crawl rate is proportionate to the number of individual URLs that are returning a server error."
  • It keeps your pages for a while: "already indexed URLs are preserved in the index, but eventually dropped." Pages that "persistently return a server error" are removed.
  • It throws away what came with the error: "Any content Google receives from URLs that return a 5xx status code is ignored." So a nice-looking error page with a 500 code counts for nothing.
  • It speeds up again once you're fixed: "Once the server starts responding with a 2xx status code, Google gradually increases the crawl rate."

So one 500 during a short outage costs you little. A page that fails every time Google comes back will fall out of the results.

Why robots.txt is the one to check first

Google's robots.txt guide spells out what happens when the file itself answers 5xx:

  • "For the first 12 hours, Google stops crawling the site but keeps trying to fetch the robots.txt file."
  • After that, "for the next 30 days Google will use the last good version", still retrying. "If there's no cached version available, Google assumes there's no crawl restrictions."

Read the first line again: the whole site, not one page. A broken robots.txt pauses crawling for everything, including the home page that loads fine for you. A new site has no "last good version" to fall back on. And a robots.txt that answers 404 is fine: Google treats a missing file as "no restrictions". Of my 191, 31 had none and that's not a problem. Only the error codes are.

Step 1: Find which addresses fail

In Search Console, open Indexing, then Pages, and click the Server error (5xx) row. You get a list of example addresses and the date Google last tried each one. Look for a pattern: all under /shop/, all search pages, or all from one day.

Then open Settings, then Crawl stats. The Host status section shows whether Google had trouble fetching robots.txt or reaching your server at all. If robots.txt shows problems there, fix that before anything else.

Step 2: Ask your site yourself

Your browser hides status codes, and it may show you a copy saved earlier. Ask the server directly. On a Mac, open Terminal; on Windows, open PowerShell and type curl.exe instead of curl. Replace the address with yours:

curl -sS -L -o /dev/null -w "%{http_code} %{time_total}s\n" https://example.com/robots.txt
curl -sS -L -o /dev/null -w "%{http_code} %{time_total}s\n" https://example.com/

Each line prints the final status code and how long it took. You want 200 (or 404 for robots.txt) in a second or two. On Windows, write NUL instead of /dev/null. Then run the same line on two or three of the addresses from Step 1. Also run the robots.txt line on the other version of your address: with www if you use the bare name, without it if you use www. Google asks each one for its own robots.txt.

Run each one twice, a minute apart. A failure that shows up both times is a real problem. A failure that comes and goes points at load or a host that struggles at certain hours. If both runs pass but Search Console still lists errors, open one address in URL Inspection and click Test live URL: that's Google asking, right now.

Step 3: Fix the cause

What fixes it depends on which code you saw.

500 on a WordPress site. Usually a plugin or theme error, often right after an update. Your host's control panel has an error log; the last lines name the file that failed. If you can't get into the dashboard, rename the wp-content/plugins folder over FTP or in the host's file manager. That switches every plugin off. If the site comes back, rename it back and switch plugins on one at a time until it breaks again.

500 or 503 only some of the time. Often the hosting plan running out of memory or allowed processes when traffic or crawling picks up. The host's resource page shows it. Caching (a cache plugin, or the host's own) means fewer pages get built from scratch, so fewer fail.

52x from Cloudflare. Cloudflare is answering for your server, so the problem is behind it. Cloudflare's 522 page lists the usual causes. Check that the server is up and that its firewall isn't blocking Cloudflare's addresses. Then check both versions of your address, with and without www, and a page other than the home page on each. In my reading, the home page forwarded fine and everything else on the same host timed out.

A robots.txt that errors while pages work. On many sites robots.txt isn't a file at all; the site's software builds it on every request, so it fails when the software fails. Putting a real robots.txt file in the site's main folder means the server hands it out directly, without running any code. A few lines is enough:

User-agent: *
Disallow:

Sitemap: https://example.com/sitemap.xml

That allows everything and points to your sitemap. If you already have rules, copy them into the file instead.

Planned maintenance. Use 503, not 500, and keep it short. Google's guide treats 503 like other 5xx codes, so a long maintenance page still slows crawling and can drop pages. Most maintenance plugins send 503 already; check with the command in Step 2 while it's on.

Step 4: Tell Google you fixed it

Run Step 2 again on the same addresses. When every one answers 200, go back to the Server error (5xx) row and click Validate fix. For your most important page, open it in URL Inspection and click Request indexing.

Crawling picks back up gradually, as Google's guide says. You don't need to wait on the validation to know you're done: your own check already tells you.

What this status doesn't mean

  • It isn't a penalty. Google slows down to avoid making things worse for your server. Once you answer 200 again, it speeds back up.
  • A handful of old errors after a fixed outage are harmless. They clear as Google comes back.
  • A good-looking error page doesn't help. Google ignores content sent with a 5xx code. What matters is the number.

If the addresses in the row are pages you deleted on purpose, they should answer 404, not 500. My guide on "Soft 404" covers how a missing page should answer, and does my site need a robots.txt covers what to put in that file.
