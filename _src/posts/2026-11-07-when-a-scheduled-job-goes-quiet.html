I have seen a scheduled task stop making progress while the machine running it stayed healthy. The process had not crashed. It was waiting behind a piece of work that the scheduler did not know was still in progress. A green “running” status would have missed the problem.

If you run a scheduled report, backup, import or automation, the useful question is not only “is the process alive?” It is “when did this job last finish something useful?” That one timestamp can catch a quiet failure before someone goes looking for the missing result.

Why process status is not enough

A process can stay alive while waiting on a lock, a network call, an unresponsive child process or an unfinished task. A scheduler may report that it started the job, but that only proves the first step happened. It does not prove that the expected output arrived.

This is why a check like “alert if the process exits with an error” has a blind spot. It catches crashes. It does not catch a job that is still running, but has not moved for an hour.

Record a useful heartbeat

After each meaningful unit of work, record a timestamp and a short status. A useful unit is something a person would notice if it never happened: a report was written, a batch was imported, a backup completed, or a message was processed.

Do not update the heartbeat just because the process is still alive. If you do, a stuck job will keep looking healthy. Update it only after the work you care about succeeds.

For a job that handles a batch, the record might contain:

  • the time the last batch completed;
  • the number of items completed, if that count is already part of the job;
  • a short success or failure state;
  • the time the next run is expected.

Keep the record somewhere the job can update and the monitor can read. A small text file or a row in a database is enough. The point is not to build a monitoring platform. It is to make the last successful result visible.

Set the alert from the job's normal interval

Choose a threshold based on how often the job normally completes. If a job usually finishes every 15 minutes, an alert after 30 minutes without a successful update gives it one missed interval before raising a flag. A daily job needs a different window. There is no universal number that fits both.

  1. Write down the expected completion interval.
  2. Allow for the longest normal run and ordinary delays.
  3. Alert when the last-success time is older than that window.
  4. Make the alert name the job, its last successful time and the next check to make.

For example: “Nightly import has not completed since Tuesday 02:10. Check the latest run log and whether it is waiting on an earlier batch.” That is more useful than “job unhealthy”.

Check the cause, not just the symptom

When a heartbeat goes stale, start with the last recorded step. Did the job start? Did it finish the previous unit? Is there an earlier run that never released a lock? Is the output file missing or unchanged? Those questions narrow the search without assuming the machine itself is down.

Also check whether the monitor can see the same heartbeat the job writes. If the job cannot update it, or the monitor is reading a different location, the alert may describe the monitoring setup rather than the job. Test both sides by making one deliberate run and confirming the timestamp changes.

Keep the signal honest

Do not label a job “healthy” just because it started on time. If you do not know whether the result is correct, say that the job completed, not that the data is correct. A heartbeat proves activity at a particular step. It does not verify every downstream effect.

For a small system, start with one last-success timestamp and one alert threshold. Add counts or per-step status only when they help someone find the failure faster. The simplest useful monitor answers three questions: what stopped, when did it last work, and what should I inspect next?
