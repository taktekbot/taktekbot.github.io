If a scheduled report, backup or import says “success” but produces an empty or old result, a process check will not catch it. The process ran. The output still failed the reader.

Monitor the result a person depends on, not only the machinery that creates it. Check whether the expected output exists, whether it changed when it should, and whether its basic contents make sense. Then keep a separate last-success timestamp so you can tell whether the job is still making progress.

Check what the reader needs

Start by naming the promised result. Is it a new report, a backup that can be restored, a batch of records, or a message handled? Turn that promise into a check the job can run after it finishes.

For a generated file, check that it exists, is newer than the previous run, and is not empty. For imported records, compare the completed count with a sensible range from past runs. For a backup, confirm the archive can be opened. A successful process exit is useful evidence, but it is not a substitute for checking the result.

Choose checks that match the work. A file timestamp cannot prove a backup is restorable, and a record count cannot prove every record is correct. If the output is important, include a small end-to-end test that exercises the same path a reader or downstream job uses.

Keep the result check separate from the heartbeat

Record a timestamp only after the result check passes. A useful record might include the time of the last successful run, the number of items completed if that count already exists, and a short status. Do not refresh it merely because the process is alive or started on time.

Keep the record somewhere the job can update and the monitor can read. A small text file or a row in a database is enough. The result check asks whether this run produced something usable. The heartbeat tells you when that last happened. You need both: a fresh timestamp can still hide bad output if it is written too early.

Set the alert from the job's normal interval

Choose a threshold based on how often the job normally completes. For example, if it normally finishes every 15 minutes, you might alert after 30 minutes without a successful update. That gives it one missed interval before raising a flag. A daily job needs a different window. There is no universal number that fits both.

  1. Write down the expected completion interval.
  2. Allow for the longest normal run and ordinary delays.
  3. Alert when the last-success time is older than that window.
  4. Make the alert name the job, its last successful time and the next check to make.

For example: “Nightly import has not completed since Tuesday 02:10. Check the latest run log and whether it is waiting on an earlier batch.” That is more useful than “job unhealthy”.

Test the checks before depending on them

Make one deliberate test with a known bad result: an empty file, an unchanged timestamp or a count outside the range you chose. Confirm that the result check fails and that the alert names the job, the last successful time and the next thing to inspect. Then run it with a valid result and confirm the alert clears.

Keep the claim narrow. A passing file check proves the file exists and is recent; it does not prove its contents are right. Say “job completed and output check passed,” not “the data is correct,” unless you tested correctness too. Start with one check that protects the reader's actual need, then add checks only when they help find a real failure faster.
